# Personal CRM

A locally-run CRM that ingests email, identifies who each message concerns, and
maintains structured, provenance-tracked bullet-point notes per contact.
Summarization runs entirely on a local LLM via [LM Studio](https://lmstudio.ai/) —
no cloud AI calls, no email content ever leaves your machine.

## How it works

1. `email_sync.py` pulls mail from Gmail (read-only) into `data/emails.json`.
2. `run.py` processes each email through the pipeline: it figures out who the
   email is about, classifies whether CC'd people are substantively involved,
   detects if a new address might belong to an existing contact, and asks the
   local LLM to extract or update short factual bullets about that person.
   Everything is written to `data/memory.json`.
3. `server.py` serves a small web frontend (`static/index.html`) for browsing
   contacts, viewing the source email behind any note, and resolving merge
   suggestions when the same person emails from a new address.

## Setup

**1. Install dependencies**
```
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

**2. Set up LM Studio**
- Install [LM Studio](https://lmstudio.ai/), download `google/gemma-4-e4b`,
  and start its local server (default: `http://localhost:1234`).
- `pipeline.py` expects the server running with that model loaded before you
  run the pipeline.

**3. Set up Gmail API access**
- In [Google Cloud Console](https://console.cloud.google.com/), create a
  project, enable the Gmail API, configure the OAuth consent screen
  (External, scope `gmail.readonly`, your account added as a test user), and
  create an OAuth client of type **Desktop app**.
- Download the client JSON and save it in the project root as
  `credentials.json`.
- Run `.venv/bin/python email_sync.py` once — it opens a browser for a
  one-time login/consent, then saves a `token.json` for future runs (auto-
  refreshed, no repeated logins needed).

Both `credentials.json` and `token.json` are gitignored — never commit them.

**4. Set your own address(es)**
The pipeline needs to know which address(es) belong to you, so it doesn't
treat your own mail as a contact. Set this from the frontend's **Settings**
panel (stored in `data/config.json`, kept separate from the CRM data itself
so resetting your notes doesn't wipe this).

## Running it

```
.venv/bin/python email_sync.py   # pull new mail from Gmail
.venv/bin/python run.py          # process new mail into notes
.venv/bin/uvicorn server:app --reload   # serve the frontend at localhost:8000
```

Re-running `email_sync.py`/`run.py` is safe and cheap — both skip anything
already processed, so only genuinely new mail costs an LLM call.

## Project layout

```
pipeline.py        # all core logic: cleaning, identification, LLM calls, merging
email_sync.py       # Gmail -> data/emails.json
run.py              # entry point: processes data/emails.json through the pipeline
server.py           # FastAPI backend serving the frontend + merge/config endpoints
static/index.html    # single-file vanilla HTML/CSS/JS frontend, no build step
data/
  emails.json         # raw inbox (gitignored, regenerated by email_sync.py)
  memory.json         # CRM output: people + bullets (gitignored, regenerated by run.py)
  config.json         # your own address(es) (gitignored, set via the Settings panel)
```

## Data model (`memory.json`)

```
{
  "people": {
    "<person_id>": {
      "display_name": str | null,
      "emails": [str, ...],
      "bullets": [
        {
          "content": str,
          "durability": "durable" | "transient",
          "ref": [email_id, ...],
          "created": "YYYY-MM-DD",
          "last_updated": "YYYY-MM-DD",
          "history": [...]
        }
      ]
    }
  },
  "email_index": {"<email>": "<person_id>"},
  "processed_emails": [email_id, ...],
  "pending_merges": {...}
}
```

`person_id` is the first-seen normalized email address for that person, not a
synthetic id. Bullets marked `transient` show as "Notes" in the frontend
(still actively changing); `durable` bullets show as "Previous Notes" (settled
facts) — that split is about durability, not recency.

## Multi-address merging

When a brand-new address emails for the first time, the pipeline checks
whether the message contains *explicit* self-identifying language matching
an existing contact (e.g. "This is Alice Chen, emailing from my personal
account") and flags a merge suggestion for review — it never merges silently.
You can also merge manually from the frontend's search results when you spot
a duplicate yourself.

## Known model limitations

Summarization runs on a small local model (`gemma-4-e4b`), which is
occasionally unreliable in specific ways this project works around rather
than fully eliminates:
- facts can occasionally get attributed to the wrong person in multi-person
  emails
- the model can rarely hallucinate a plausible-sounding but unstated fact
- restated existing facts sometimes come back tagged as "new" — caught by a
  word-overlap dedup check before they'd create a duplicate bullet
